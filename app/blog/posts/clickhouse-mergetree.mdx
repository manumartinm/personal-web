Yesterday I was a bit tired of studying, so I opened my editor and hacked together a small C++ project to understand the internals of ClickHouse a little better.

I’ve used ClickHouse a lot at Tinybird (and earlier at Keytrends), and I’ve always had that engineer curiosity: **what if I implement a tiny version of MergeTree from scratch?** Just to learn the fundamentals.

So I built a minimal (but functional) MergeTree-like engine in C++ (the code is on GitHub: [manumartinm/clickhouse-mergetree](https://github.com/manumartinm/clickhouse-mergetree)). In this post, I’ll explain the ideas behind it, the trade-offs, and how the end-to-end flow works.

## Academic Fundamentals: Some math & papers

### LSM-Trees

The **LSM-Tree** (Log-Structured Merge-Tree) concept was introduced in the classic paper ([O’Neil et al., 1996](https://www.cs.umb.edu/~poneil/lsmtree.pdf)). The core idea is:

> _Instead of updating data in-place like traditional B-trees, keep data in immutable structures and merge periodically_

This approach solves the **write amplification problem** that traditional systems suffer from. In a B-tree, a single write can generate multiple random I/Os. In an LSM-tree, all writes are sequential.

### Column Stores

The C-Store paper ([Stonebraker et al., 2005](https://people.brandeis.edu/~nga/papers/VLDB05.pdf)) established the foundations of columnar storage:

- **Better compression**: Similar data compresses better together
- **Selective I/O**: Only read the columns you need
- **Vectorization**: SIMD operations over homogeneous arrays

### Sparse Indexing

Unlike traditional dense indexes, ClickHouse uses a **sparse primary index**. The high-level idea (indexing blocks, not rows) is common in LSM/SSTable systems (e.g., [Chang et al., 2006](https://static.googleusercontent.com/media/research.google.com/en//archive/bigtable-osdi06.pdf)) and is documented clearly in ClickHouse’s own docs ([ClickHouse, n.d.-b](https://clickhouse.com/docs/optimize/sparse-primary-indexes)).

- **Dense index**: One entry per row → O(N) memory
- **Sparse index**: One entry every 8192 rows → O(N/8192) memory

For a billion-row table, this means 122K index entries vs 1B. The difference is abysmal.

## Let's get to code

After studying these papers and working with ClickHouse in production, I built my own implementation with the help of Claude Code. Here are the key decisions:

### 1. Basic Data Structures: Rows and Granules

```cpp
struct Row {
    std::string key;
    std::string value;
    uint64_t timestamp;

    bool operator<(const Row& other) const {
        if (key != other.key) return key < other.key;
        return timestamp < other.timestamp;
    }
};
```

**Granules** are blocks of 8192 rows—the size ClickHouse found optimal after years of production tuning:

- Index overhead (too small → many entries)
- Query selectivity (too large → read irrelevant data)
- Efficient memory mapping (OS page size alignment)

### 2. MemTable with Skip Lists: Probabilistic Elegance

```cpp
class MemTable {
private:
    static constexpr int MAX_LEVEL = 16;
    static constexpr double PROBABILITY = 0.5;
    std::shared_ptr<SkipListNode> header_;

public:
    void insert(const Row& row);  // O(log n) expected
    RowVector query(const std::string& start, const std::string& end) const;
};
```

I chose **skip lists** over B-trees because:

1. **Concurrency**: Skip lists are inherently more thread-friendly
2. **Simplicity**: Fewer corner cases, fewer bugs
3. **Memory locality**: Better for write-heavy workloads

Pugh’s original paper is still a great read ([Pugh, 1990](ftp://ftp.cs.umd.edu/pub/skipLists/skiplists.pdf)).

### 3. Columnar Storage: The MergeTree Magic

Each **Part** is immutable and stores data in columnar format:

```
part_001/
├── metadata.bin       # Part statistics
├── primary.idx        # Sparse primary key index
├── granule_0_keys.bin       # Key column
├── granule_0_values.bin     # Value column
├── granule_0_timestamps.bin # Timestamp column
└── ...
```

This organization enables what C-Store called **late materialization**: you only reconstruct full rows when you actually need them ([Stonebraker et al., 2005](https://people.brandeis.edu/~nga/papers/VLDB05.pdf)).

### 4. Merge Algorithm: K-Way Merge with Priority Queue

```cpp
class MergeIterator {
private:
    std::priority_queue<RowWithSource> heap_;
    std::vector<std::unique_ptr<Part>> parts_;

public:
    Row next();  // O(log k) where k = number of parts
    bool has_next() const;
};
```

The merge algorithm is a classic **k-way merge** using a heap. While conceptually simple, the decisions of _when_ to merge are complex. My implementation uses simple heuristics, but in production ClickHouse has sophisticated algorithms that balance:

- **Write amplification** (don't merge too frequently)
- **Read amplification** (don't have too many parts)
- **Space amplification** (temporary storage during merges)

### 5. Compression is Critical

My implementation has no compression, but in production it’s **fundamental**. ClickHouse supports multiple codecs (see the docs: [ClickHouse, n.d.-c](https://clickhouse.com/docs/sql-reference/statements/create/table#column-compression-codecs)), and the common theme is always the same: trade CPU for I/O.

- **LZ4**: Fast, decent ratio
- **ZSTD**: Better compression, more CPU
- **Specialized codecs**: Delta, DoubleDelta, Gorilla for time series

At Tinybird we saw 10:1 ratios or better on real data.

## Code Deep Dive: How It Actually Works

One very important thing about LSM designs is this: **writes are cheap because we append immutable sorted data**, and then we pay the cost later by compacting/merging parts in the background ([O’Neil et al., 1996](https://www.cs.umb.edu/~poneil/lsmtree.pdf)).

Here’s the mental model of the implementation:

```
INSERT → MemTable (sorted in RAM) → FLUSH → Part on disk (immutable)
QUERY  → MemTable + relevant Parts → merge results → deduplicate
MERGE  → pick Parts → k-way merge → new bigger Part → remove old Parts
```

### 0. The invariants (what must always be true)

- **Sorted order**: every structure we query efficiently is sorted by the same order (in my case, primary key + timestamp). This is what makes range queries and merges simple.
- **Immutability on disk**: once a `Part` is written, we never update it in place. If we need a “new version”, we create a new `Part` (via flush or merge).
- **A sparse index per part**: not “one entry per row”, but “one entry per granule”. This is the key trick that keeps memory/index size low (see also: [ClickHouse, n.d.-b](https://clickhouse.com/docs/optimize/sparse-primary-indexes)).

### 1. Write path (INSERT → MemTable → FLUSH → Part)

**Step A: Insert hits the MemTable.**  
The MemTable is an in-memory ordered structure (skip list). That means inserts are cheap-ish (\(O(\log n)\) expected) and, crucially, **the MemTable can give you rows already sorted** when it’s time to flush.

**Step B: When MemTable is “big enough”, we flush.**  
Flush is the moment where we turn RAM state into an immutable on-disk `Part`. Conceptually the steps are:

- **Snapshot sorted rows** from MemTable (so we freeze a consistent view).
- **Split into granules** of fixed size (8192 rows in my implementation).
- **Write columns** for each granule (`keys`, `values`, `timestamps`) to separate `.bin` files.
- **Build the sparse index** (`primary.idx`) with one entry per granule (typically min/max key per granule).
- **Register the part** in the MergeTree’s list of parts.

The important insight: flushing creates **more parts**. That’s fine for writes, but it increases the number of files/segments a query might have to look at (read amplification). That’s why merges exist.

### 2. What exactly is inside a Part?

A `Part` is basically:

- **A set of granules** (fixed-size blocks of rows).
- **Per-granule column files** (columnar layout): you can read only what you need.
- **A sparse primary index** to quickly decide which granules might overlap your query range.

This is a tiny but very practical approximation of ClickHouse’s “parts + marks” idea: don’t index every row; index blocks.

### 3. Read path (QUERY → prune parts → prune granules → scan)

When you do a range query `[start_key, end_key]`, the engine does three levels of “filtering” before it reads data:

**Level 1: MemTable (fresh writes).**  
Always check MemTable because it contains the newest rows that might not have been flushed yet.

**Level 2: Part-level pruning.**  
Each part can be skipped quickly if its global min/max key doesn’t overlap the requested range.

**Level 3: Granule-level pruning (sparse index).**  
Inside a part, we don’t scan everything. We ask the sparse index which granules _might_ overlap:

```cpp
bool IndexEntry::overlaps_range(const std::string& start_key,
                               const std::string& end_key) const {
    return !(max_key < start_key || min_key > end_key);
}
```

Then we only load/scan those granules. In a “real” column store, this is also where the engine decides **which columns** to read. My minimal version reads the columns needed to reconstruct `Row` objects for results.

### 4. Merging query results (why we “merge and dedup”)

Because we never update parts in place, you can have multiple versions of the “same logical key” across different parts (and also in the MemTable).

So the final query result is:

- **Merge** the sorted streams (MemTable + each part’s results) into one sorted stream.
- **Deduplicate** by key/versioning rule (in this project: keep the latest by `timestamp`).

My code currently does this in a very simple way by concatenating results, sorting, and `unique`-ing. It’s not the most efficient approach, but it’s conceptually clean for an educational implementation. A production engine would do this as a streaming merge of already-sorted iterators to avoid extra memory/sorts.

### 5. Background merges (why we compact parts at all)

Every flush adds a new part. If we never merge, reads get slower because:

- you have to check more parts,
- you might have to scan more granules,
- you do more merging/dedup work at query time.

So merges (compactions) trade **write amplification** for lower **read amplification**:

- Pick a few candidate parts (heuristics: size tiers, number of parts, etc.).
- Do a **k-way merge** of their rows (because each part is sorted).
- Apply the same dedup rule (keep the newest version).
- Write out a **new bigger part** and drop the old ones.

The “k-way merge” is the classic algorithmic core: you keep a min-heap with the current head row of each input part, pop the smallest, advance that input, repeat. That’s exactly the same shape you’d use in merge sort—just generalized to \(k\) inputs.

### 6. A tiny worked example (with numbers)

To make the flow tangible, let’s pretend:

- the **granule size is 4 rows** (instead of 8192),
- the sort order is **(key, timestamp)**,
- and the “versioning rule” is **latest timestamp wins**.

Now we insert these rows (same key can appear multiple times):

| insert order | key | value | ts  |
| ------------ | --- | ----- | --- |
| 1            | `a` | `v1`  | 10  |
| 2            | `b` | `v1`  | 11  |
| 3            | `a` | `v2`  | 12  |
| 4            | `c` | `v1`  | 13  |
| 5            | `b` | `v2`  | 20  |

**After inserts 1..4**, MemTable hits the flush threshold and we write **Part_1**.
Because MemTable is ordered, the flushed rows are already sorted:

```
Part_1 rows (sorted):
(a,10) (a,12) (b,11) (c,13)
```

**Insert 5** stays in MemTable for now:

```
MemTable:
(b,20)
```

Now query the range `[a, b]`:

- MemTable returns `(b,20)`
- Part_1 returns `(a,10) (a,12) (b,11)`
- merge + dedup keeps the newest version per key:

```
Result:
a → (a,12)
b → (b,20)
```

This example is basically the whole system in miniature: **immutability creates duplicates across structures**, and the engine resolves them by merging and applying a “latest wins” rule.

### 7. A “drawing” of the system (what lives where)

Here’s the physical picture of one `Part` on disk in my project:

```
MergeTree/
  parts/
    part_1/
      metadata.bin
      primary.idx            # sparse index (1 entry per granule)
      granule_0_keys.bin
      granule_0_values.bin
      granule_0_timestamps.bin
      granule_1_keys.bin
      ...
```

And here’s how a query uses that layout:

```
query(start_key, end_key)
  ├─ read MemTable (sorted in RAM)
  ├─ for each Part:
  │    ├─ check part min/max (cheap prune)
  │    ├─ consult primary.idx to pick candidate granules
  │    └─ read only those granule_*_{keys,values,timestamps}.bin
  └─ merge + dedup across all sources
```

### 8. Math notes (simple but useful)

**Skip list insert (MemTable).**  
Expected insertion/search cost is \(O(\log n)\). With promotion probability \(p = 0.5\), the expected number of levels per node is constant, so you get a fast ordered structure without explicit rebalancing ([Pugh, 1990](ftp://ftp.cs.umd.edu/pub/skipLists/skiplists.pdf)).

**Sparse index size.**  
If a part has \(N\) rows and granule size \(S\), the number of index entries is:

\[
E = \left\lceil \frac{N}{S} \right\rceil
\]

So compared to a dense index (\(N\) entries), you reduce it by roughly a factor of \(S\) (8192 in my “real” implementation).

**K-way merge cost.**  
If you merge \(k\) sorted inputs with total \(R\) rows, heap-based k-way merge is:

\[
O(R \log k)
\]

That’s why having too many parts (large \(k\)) hurts reads, and why compaction/merges matter.

**A tiny cost model (intuition, not a proof).**  
For a range query, you can think:

\[
T \approx c*0 \cdot P + c_1 \cdot \sum*{p=1}^{P} E_p + c_2 \cdot R
\]

Where:

- \(P\) = number of parts you “touch”,
- \(E_p\) = index entries scanned/checked in each part (worst-case; in practice you can binary search),
- \(R\) = total rows actually scanned/returned.

Merges aim to reduce \(P\) (and usually \(R\) for the same logical query) at the cost of doing extra work in the background.
